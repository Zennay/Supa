# Future M5 offline comparison: distinct inspected-source objects

**Product-core 1/2:** [issue #2343](https://github.com/Zennay/Supa/issues/2343) isolates the next *in-memory only* historical-provenance issue after frozen hosted-green [DRAFT #2342](https://github.com/Zennay/Supa/pull/2342), head \`85636ceaa3f3fed523d2106a94ca0a5247913e5c\` (1,247/1,247 Node green, npm high audit/M1/build green).

A caller could supply two different inspection envelopes and separately allocated arrays, but populate both with the exact **same JS source object**. Before this change, the pure comparer accepted both as independent captures and could report P3 unchanged, although the historical row was just the current mutable source reused. The previous #2342 root/array identity check is necessary but does not cover nested source-identity aliasing.

After bounded, own-property cohort snapshotting and same root/array refusal, the comparer now checks identity of every non-null inspected object/function across the pinned current and baseline arrays. If a source is shared, it throws the existing opaque \`Invalid or unbounded baseline inspection\` without invoking a source getter/iterator or echoing its ID. This applies to verified and failed captures alike. Independently allocated objects with *identical fictional data* are still valid P3 **manual-only** comparisons; copies do not prove actual independent historic capture.
